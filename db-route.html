テーブル同士の繋がり


users ──┬──< refresh_tokens
        │
        └──< orders ──< order_items >── products ─── inventories

refresh_tokens.user_id     → users.id
orders.user_id             → users.id
order_items.order_id       → orders.id
order_items.product_id     → products.id
inventories.product_id     → products.id   （主キーを兼ねる。だから1商品に在庫行は1つ）

  
    
    
  • ──< は「1つに対して複数」。1人のユーザーが複数の注文を持ち、1つの注文が複数の明細を持つ。
    • 
    
  • 繋がりはすべて「子テーブルが親の id を列として持つ」形。親は子のことを知らない（orders に明細の id は入っていない）。
    • 
    
  • products と inventories だけは1対1。在庫行は注文のたびに書き換わるので、商品マスタと行を分けてある。
    •

  • ✓ の操作は複数テーブルを「全部成功か全部失敗か」で書く必要がある。これがトランザクション境界を service に置く理由。
    • 
    
  • inventories だけが4種類の操作から UPDATE され、しかも注文は複数ユーザーから同時に来る。だから排他制御の舞台がこのテーブルになる。
    • 
    
  • order_items は INSERT されたら二度と変わらない記録。orders も変わるのは status だけ。

シナリオのために仮置きしている前提

  
    
    
  • 管理者アカウントは登録 API ではなく初期データとして投入する。
    • 
    
  • 商品登録と同時に在庫行を 0 / 0 で作る（products と inventories を1トランザクションで）。
    • 
    
  • 入荷（quantity_on_hand を増やす）操作がある。これが無いと在庫が 0 のまま増えない。
